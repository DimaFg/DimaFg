# Архитектура backend

Backend остаётся модульным монолитом на FastAPI и PostgreSQL. Разделение слоёв взято
из attendance-bot и event-service с учётом размера этого проекта. HTTP API, схема БД,
миграции и команды `python -m app.cli …` сохранены.

## Слои и зависимости

| Каталог | Ответственность |
|---|---|
| `domain` | Типы, нормализация контакта, состояние новой заявки, сообщение уведомления |
| `application` | Сценарии `CreateLead` и `NotifyLead`, порядок проверок и операций |
| `port` | Протоколы репозиториев, часов, UoW, доставки и чтения публичного каталога |
| `adapter` | SQLAlchemy, транзакционные блокировки, обработчик outbox, Telegram/SMTP, пароли |
| `presentation/http` | HTTP-контракты, валидация Pydantic, маршруты, перевод ошибок, middleware |
| `di` | Сборка сценариев и адаптеров с общей сессией на запрос |
| `core` | Конфигурация, JSON-логи, HMAC, heartbeat и эксплуатационные проверки |

`domain` не зависит от инфраструктуры. `application` использует доменные типы и порты,
не импортирует FastAPI, SQLAlchemy или Pydantic. ORM-объекты не выходят в HTTP-обработчики:
адаптер чтения возвращает dataclass-проекции, а сценарий создания — публичный номер.
HTTP-ошибки создаются только в presentation. Проверка границ находится
в `api/tests/test_architecture.py`.

Простое чтение услуг и портфолио проходит через `PublicCatalog`. Дополнительные обработчики
и агрегаты для этих запросов пока не нужны. SQL и правила публичной выборки находятся
в `adapter/database/catalog.py`.

## Создание заявки

1. HTTP-слой валидирует запрос и создаёт `CreateLeadCommand`.
2. Сценарий нормализует контакт и получает транзакционные блокировки для контакта, IP-отпечатка
   и ключа идемпотентности. Все блокировки берутся в одинаковом порядке.
3. Повтор с сохранённым ключом возвращает исходную заявку, даже если тело изменилось:
   это сохраняет существующее поведение API.
4. Проверяются услуга и дубликат. Дедупликация учитывает контакт, текст, услугу и причину
   спама: корректная заявка не должна потеряться из-за предыдущей слишком быстрой отправки.
5. Лимиты проверяются только для новой заявки. Повтор уже принятой заявки получает 200.
6. Заявка, история и outbox сохраняются одной транзакцией. При ошибке, включая flush,
   выполняется rollback. Для spam-заявки outbox не создаётся.

PostgreSQL advisory locks предотвращают гонки между worker-процессами API без изменения
таблиц. Реализация рассчитана на стандартный для приложения уровень READ COMMITTED.
Прямые записи в таблицу в обход сценария не получают этих гарантий.

## Уведомления и outbox

`NotifyLead` получает сообщение через `NotificationRepository` и отправляет его через
`Sender`. После каждого успешного канала вызывается порт `DeliveryProgress`: адаптер
сохраняет канал в `payload.done` отдельным commit до следующей отправки. Сценарий не
управляет SQL-транзакцией. После завершения каналов worker фиксирует итоговый статус.

Worker выбирает задание через FOR UPDATE SKIP LOCKED и получает неблокирующую session
advisory lock на его ID. PostgreSQL-соединение закреплено за заданием до конца обработки:
блокировка сохраняется между commit отдельных каналов. Другой worker пропускает занятое
задание, даже если истёк `locked_at`, и может обработать следующее. Номер попытки меняется
только после успешного получения блокировки.

В конце обработки блокировка явно освобождается перед возвратом соединения в pool,
в том числе при исключении. Если освобождение не удалось, соединение инвалидируется.
После падения процесса блокировка освобождается при закрытии соединения с PostgreSQL,
а задание восстанавливается после таймаута. Worker должен подключаться к PostgreSQL
напрямую либо через session pooling; transaction pooling не подходит для session locks.

Ошибка сохранения прогресса останавливает дальнейшую отправку; незавершённое задание
будет повторно захвачено после таймаута. Уже сохранённые каналы при этом пропускаются.
Временные и неожиданные ошибки ограничены `max_attempts`;
для неожиданных исключений сохраняется только имя типа,
чтобы не записать персональные данные. Некорректный `lead_id` завершает задание как failed.

Доставка имеет семантику at least once: падение после фактической отправки, но до commit
может привести к повторному уведомлению. Транзакция PostgreSQL не может атомарно подтвердить
внешнюю отправку Telegram/SMTP. При штатном повторе сохранённые успешные каналы пропускаются.

## Развитие

Админские команды изменения статуса, публикации фото и постановки медиа в обработку
добавляются как отдельные application-сценарии. В domain следует переносить реальные
инварианты по мере реализации этих функций. Универсальные CRUD-репозитории, брокер событий,
микросервисы и общий базовый класс агрегатов сейчас не требуются.

Синхронный SQLAlchemy сохранён; переход на async требует отдельной причины и проверки.
Модели auth, audit и медиа перенесены в адаптер хранения, но соответствующие функции из ТЗ
ещё предстоит реализовать — сам перенос не делает их готовыми.
